## 用一句话对齐「产品级」定义

当前状态更接近：**结构认真、契约清晰、文档强于平均 indie 的「高完成度可用版」**。

到**产品级发布**，客观上还差的核心不是「是不是 AI 写的」，而是：

1. **测出来的信心**（自动化 + 手工首发矩阵）  
2. **首装与环境失败的可恢复性**  
3. **权限、隐私、升级**三条对外承诺能说清、做得到  

若选择「到产品级再发」是合理的；可将下文 **P0 五条**当作发布门槛，**P1** 作为发后一两个迭代内收尾，不必等成「平台级」才发。

## P0：不补就容易在首发翻车

### 1. 测试与质量闸门

- 前端 Vitest 目前偏「烟测」量级；**关键路径**（发消息、切角色、装插件、目录插件 RPC、导入角色包、设置持久化）缺少**稳定、可重复**的自动化覆盖。  
- **产品级**通常要求：至少一条「安装 → 开聊 → 关应用再开」的 e2e 或半 e2e，加上核心 `invoke` 的集成测试矩阵（不必 100% 覆盖，但**不能只有 smoke**）。

### 2. 首发安装与运行环境

- Windows / 路径 / 杀毒 / 权限 / Ollama 未启动 / 模型名错误——**首周工单会集中在这里**。  
- 差距：**安装包内或首次启动的「环境自检」**（可选模型探测、roles 路径提示、插件目录说明）、**离线/失败时的可读下一步**（i18n 已在推进，要把「首装失败」当一等公民文案）。

### 3. 崩溃、遥测与隐私

- 若已有 Sentry 等，要明确：**默认开关、隐私说明、脱敏规则**。  
- 产品级需要：**可诊断（日志/错误码）+ 用户可控（关遥测）+ 文档一句话说清**。

### 4. 数据与安全边界（插件）

- 目录插件 / MCP / 网络权限——规则里已有方向，**产品级**要的是：**用户能理解「为什么弹窗」、拒绝后行为可预测、审计可查**。  
- 差距：把「高风险能力」做成**可演示的验收清单**（每条对应 UI + 降级文案），而不是只写在文档里。

### 5. 版本、兼容与升级

- 角色包 schema、主程序版本、编写器/启动器——**破坏性变更**要有「谁兼容谁」的一页表 + 迁移提示。  
- 产品级：**semver 或等价策略**、changelog、**「从 x 升到 y」**最短步骤。

## P1：不挡发布，但会决定「像不像成熟产品」

### 6. 国际化与文案收尾

- 主路径已推进，但**全界面英文仍可能有漏网**；产品级常要求「切换语言后无残留中文」在**承诺范围内**（可单独声明「创作者文档英文仍在补」）。

### 7. 性能与资源

- 仓库已有性能/分包与 baseline 文档；产品级要：**低端机/冷启动/大会话**的底线数字或「已知限制」公开一句，避免被当成 bug 骂。

### 8. 无障碍与基础 UX

- 键盘流、焦点、错误恢复、长任务进度——不必一次做完，但**高频操作**不应只靠鼠标。

### 9. 支持渠道与预期管理

- Issue 模板、常见问题、Discord/群/邮件**选一个主入口**；产品级是：**用户知道去哪反馈、团队知道怎么收**。

### 10. 法律与分发

- 第三方模型、插件市场、用户生成内容——**最低限度**：README 里许可证、免责声明、数据落盘位置（文档已有部分，**首发前再扫一遍「用户会问的三句话」**）。
