## A. 内核与运行时

### 1. 按槽位语义的合并代数

**一句话**：同一功能槽位挂多个插件实例时，不采用“统一合并”，而是按槽位语义选择合并策略。

**问题**

插件化对话系统通常允许一个槽位挂多个实现。常见做法是框架统一处理：要么“取最后一个”，要么“全部并行后投票/拼接”。这会在三类槽位上同时出错：

- 状态类（情绪、事件、Prompt）：多个实例产生互斥结果，并行聚合没有意义；
- 检索类（记忆）：取最后一个会丢掉其他实例召回的互补条目；
- 生成类（LLM）：有时要最低时延，有时要高可用，有时要保留最后一份，统一策略表达不了。

**做法**

1. 解析槽位实例列表：空 → 缺省实现；单实例 → 直接调用；多实例 → 按语义进入合并分支。
2. 状态类：按注册顺序串行调用，成功结果覆盖，失败跳过，取最后一个有效结果。
3. 检索类：串行调用各实例，按记忆唯一标识去重取并集，再按重要度×权重排序、按上限截断。
4. 生成类：按配置选竞速（最先成功者胜并中止其余）、失败回退（首选失败才用下一个）或串行末位胜出。
5. `none` 显式关闭：检索返回空、情绪返回中性、事件忽略；Prompt/LLM 这类必需槽位在启动健康检查阶段直接拦截，不静默回退。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/slot_runner.rs`
- `kernel/crates/oclive_kernel_host/src/state/host_backends.rs`（折叠后的六槽）
- `kernel/crates/oclive_validation/src/plugin_backends.rs`（`PluginBackends` 定义）
- `kernel/crates/oclive_kernel_host/src/domain/backend_registry/`

**和常见做法差在哪**

LangChain 一类框架有 fallback、router、ensemble，但通常是“某类组件有某种策略”；这里把“槽位语义 → 合并代数”做成统一规则，并把 `none` 的语义和启动期拦截一起定义。单看每条都不新，合起来是一套可配置、可测试、可解释的运行时策略。

**视频钩子**

> “同一个记忆槽，我插了三套记忆。现在召回结果有三份，谁说了算？”

可拍画面：同一角色配置 1 个/2 个/3 个记忆插件，展示召回条数与重复率变化。

**边界**

- “状态/检索/生成”是启发式分类，Agent、Event、Prompt 的边界仍有讨论空间。
- 竞速策略依赖真正的取消语义；取消不彻底会留下后台任务。
- 这套策略解决“怎么合并”，不解决“某个插件实现好不好”。

### 2. 焊接式双构建态

**一句话**：同一套编排，运行时可以插件化装配，编译期也可以把选定槽位“焊死”成静态直调，生成两个可执行目标。

**问题**

可插拔与低时延是一对矛盾：

- 插件化要动态分发、运行时解析，嵌入式/低时延场景嫌重；
- 手工写一份“固化版”容易和可插拔版漂移，两份行为不一致；
- 没有基准对比，就不知道“焊接”到底省了多少。

**做法**

1. 脚手架生成项目骨架 + 一份焊接配置，声明要焊接的功能键。
2. 从单一“焊接桩模板源”生成各功能的静态实现，避免和可插拔版漂移。
3. 生成一条静态直调的一轮处理路径，替代“插件宿主解析 + 动态分发”。
4. 生成两个入口：标准可插拔二进制、高耦合单体二进制，共享同一份功能逻辑。
5. 构建时按配置再生成；用基准工具跑两种二进制，保存时延/内存对比历史。

**代码锚点**

- `monolith.toml`（`weld_modules`）
- `kernel/crates/oclive-cli/src/monolith_codegen.rs`
- `creator-docs/rfc/RFC_OCLIVE_MONOLITH_MODE.md`

**和常见做法差在哪**

静态链接、编译期 DI、代码生成都不新；把“同一套 LLM 编排”做成双构建态、并要求单一模板源 + 基准对比，这个组合在 AI 角色运行时里不常见。它的价值在硬件/嵌入式宿主：同一颗内核，开发时插件化，量产后焊死降开销。

**视频钩子**

> “同一份代码，我编译了两次：一次能换零件，一次焊死。为什么？”

可拍画面：两个二进制并排跑同一段对话，展示启动时间/时延差异。

**边界**

- 双构建态本身有维护成本；没有基准数据就不该默认开启。
- 焊接只适合“确定不再替换”的部署；不是所有场景都该焊。
- 当前主要是构建/基准能力，真实量产收益仍需硬件实测。

### 3. 统一资源协调器

**一句话**：把 GPU/内存/CPU 的“谁先上、谁让路、谁降级”集中决策，适配器只负责执行。

**问题**

一个角色运行时同时要跑：本地 LLM、TTS、ASR、Live2D/渲染、可能的视觉模型。它们抢同一块 GPU/内存：

- 各自探测、各自启动，容易 OOM 或互相拖慢；
- “失败就重试”会放大资源冲击；
- 第三方扩展如果自己能分配资源，宿主就失去了安全边界。

**做法**

1. 蓝图/Profile/设备状态 → 编译成**只读候选计划**（不调用适配器、不改租约）。
2. 执行前再做 revision/controller 复核，防止计划过期。
3. 租约（lease）+ 准入（admission）：没有租约不执行。
4. 可逆抢占：`yield-then-run`，先让出再启动，失败可回退。
5. 适配器 owner-scoped 注册：第三方只能管自己的资源；blocked/degraded 原因可诊断。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/resource_plan.rs`
- `kernel/crates/oclive_kernel_host/src/domain/resource_coordinator/{admission,lease,transition}.rs`
- `creator-docs/rfc/RFC_BLUEPRINT_EXTENSION_AND_RESOURCE_COORDINATION.md`

**和常见做法差在哪**

常见做法是“每个子系统自己管显存”或“一个全局 GPU 锁”；这里是集中决策、适配器执行、租约化、可逆抢占，并且把“计划”和“执行”分开。对多模型/多模态/硬件宿主，这是刚需。

**视频钩子**

> “一个 7B 模型、一个 TTS、一个 Live2D，同时开，怎么不打架？”

可拍画面：资源面板显示租约/排队/降级；故意让两个重任务竞争，展示排队而不是 OOM。

**边界**

- 首期聚焦 GPU；CPU/内存/多设备是预留，不是全部已验证。
- 真实设备矩阵、长时 soak、功耗仍未完成。
- 调度策略的公平性/抢占收益需要实测数据。

### 4. 聊天请求回执：一次发送只进回合一次

**一句话**：给每次发送一个回执，跨传输、重试、崩溃都只允许一个回合真正执行。

**问题**

桌面端可能同时有 Tauri IPC、本机 HTTP、重连恢复；用户点两次、客户端超时重试、进程崩溃重启，都可能让同一条消息：

- 被回复两次；
- 被写库两次；
- 被计费两次；
- 或者第一次其实成功了，客户端却以为失败又发一次。

**做法**

1. 客户端带 `client_request_id`（规范 UUID）。
2. `scope = role + session`，`fingerprint = 语义字段 SHA256`（排除 `client_request_id`）。
3. 原子 `claim`：抢到才执行；抢不到进入恢复流程。
4. 回执状态：`running → completed / unconfirmed`。
5. **超时、崩溃、取消都不回收**；只允许恢复 `completed`；等不到就返回“结果未确认”，绝不自动重发。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/chat_engine/request_receipt.rs`
- `kernel/crates/oclive_kernel_host/migrations/040_chat_request_receipts.sql`
- 同目录 `request_receipt/tests/`

**和常见做法差在哪**

幂等键是常见模式；这里的关键是“回合语义 + 不回收 + 未确认状态”：它承认“可能已经执行”，而不是假装失败可以安全重试。对本地优先、跨传输的聊天应用，这是可靠性地基。

**视频钩子**

> “我点两次发送，为什么只回了一次？如果第一次其实成功了，第二次会怎样？”

可拍画面：断网/杀进程/重连，展示“未确认”提示与恢复结果。

**边界**

- 需要客户端配合传 ID；不传就退化为普通路径。
- 分阶段成人节拍有独立 generation 身份，不走这条。
- “未确认”是诚实的结果，不是自动修复；产品要设计好提示。

## B. 记忆与情绪

### 5. 记忆三套存储 + 离线回放

**一句话**：聊天记录、短期记忆、长期记忆是三套存储；删聊天不清记忆，换聊天后端也能重建记忆。

**问题**

大多数聊天应用把“聊天记录”当“记忆”。这会带来三个问题：

- 用户删聊天记录，角色就“失忆”，产品语义不对；
- 换聊天存储后端，记忆逻辑要重写；
- 从历史对话重建记忆时，容易重复写入、越写越多。

**做法**

1. 三个存储域：聊天记录（可替换后端）、长期记忆（固定表）、短期记忆（最近 N 轮）。
2. 编排上下文只从长期/短期记忆取，不把聊天记录当记忆源；删聊天不碰记忆表。
3. 聊天存储接口带能力探测（是否支持检索/回放/自动清理），前端据此隐藏不可用操作。
4. 混合后端：权威库同步写，文件镜像异步追加（临时文件 + 原子改名）。
5. 离线回放：从任意后端读历史 → 配对回合 → 复用实时记忆策略 → 相似合并写入。
6. 相似合并：关键词重叠（Jaccard + 4-gram）达标则“提及计数 +1”，不覆盖原文；否则新增。提及越多，时间衰减越慢。

**代码锚点**

- `kernel/crates/oclive_kernel_runtime/src/domain/memory_engine.rs`
- `kernel/crates/oclive_kernel_host/src/infrastructure/chat_storage/replay.rs`
- `kernel/crates/oclive_kernel_host/src/infrastructure/db/memory_merge.rs`
- 迁移 `027/028/034`

**和常见做法差在哪**

“聊天与记忆分开”是产品语义决策；“从任意聊天后端回放、用同一套策略重建、非覆盖式合并”是工程闭环。没有向量嵌入也能抑制重复膨胀，适合端侧。

**视频钩子**

> “我把聊天记录全删了。她还记得我吗？”

可拍画面：删聊天 → 记忆页仍在 → 角色提起旧事；再演示回放重建。

**边界**

- 相似度是轻量关键词度量，不是语义理解；误报/漏报都存在。
- 记忆“质量”（该记什么、该忘什么）仍取决于策略与模型，不是表结构能解决的。
- 回放是异步任务，长历史需要进度与错误处理。

### 6. 跨轮复杂情感延迟注入

**一句话**：本轮只分析情感、写成“给下一轮”的叙事提示；下一轮 Prompt 构建时再注入。

**问题**

如果本轮分析出的情感立刻注入本轮 Prompt，会形成因果倒置：用“还没生成的回复”去指导“这次生成”。结果要么自激，要么把角色锁在一种情绪里。

**做法**

1. 用 `srid = role + session` 做命名空间，多会话/多角色不串。
2. 本轮 Prompt 构建前，读取上一轮留下的“复杂情感叙事提示”。
3. 作为独立段落注入 Prompt（不塞进六槽配置）。
4. 生成回复后，再分析本轮复杂情感，转写成“下一轮”的叙事提示。
5. 写入会话缓存 + 持久化表；进程重启后可恢复。
6. 异地/远程路径可跳过，避免不必要的状态污染。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/chat_engine/turn_pipeline/pre.rs`
- `.../turn_pipeline/co_present/run_middle.rs`
- `.../turn_pipeline/post/post_llm.rs`
- 迁移 `015/026`

**和常见做法差在哪**

常见做法是“本轮情绪 → 本轮 Prompt”；这里是“本轮分析 → 下一轮注入”，把情感连续性做成跨轮状态，而不是当轮提示词拼接。时序是这条机制的核心。

**视频钩子**

> “她昨天没说完的那点情绪，今天还在。”

可拍画面：连续两轮对话，第二轮开头角色承接上一轮的情绪。

**边界**

- 延迟注入可能带来“过期情绪”；需要评测与衰减。
- 叙事提示是自然语言，模型是否遵循仍需真实模型验证。
- 不是所有路径都该注入（异地/远程可跳过）。

### 7. 虚拟时间人格演化

**一句话**：人格 = 核心人格 + 人格增量；交互改增量，虚拟时间让增量回归核心。

**问题**

常见角色人格要么固定，要么只随交互单调累积。角色三天没被打开，回来还是上次的状态——“久别淡化”不成立。

**做法**

1. 核心人格（出厂基线）+ 人格增量（后天偏移），当前人格 = 核心 + 增量（边界裁剪）。
2. 维护虚拟时间：真实时间锚点 + 虚拟锚点 + 流速；非沉浸模式取真实时间。
3. 交互事件调整增量；可选地，被反复提及的记忆做小幅强化。
4. 按虚拟时长让增量向零衰减（即向核心回归）；增量为零时不写库。
5. 空闲补算：下次交互前，按空闲虚拟时长补一次衰减。
6. 时间跳变：手动改时间时，按跨越的虚拟时长补算；固定档案模式跳过衰减。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/virtual_time_sync.rs`
- `kernel/crates/oclive_kernel_host/src/domain/time_driven_evolution.rs`
- 迁移 `005/023/035`

**和常见做法差在哪**

“人格随交互变化”不新；“核心/增量分离 + 虚拟时间驱动回归 + 空闲补算 + 时间跳变”这套组合，是把角色“时间感”做成运行时状态，而不是文案设定。

**视频钩子**

> “三天没来，她对你的态度会变淡——不是我写的台词，是时间算出来的。”

可拍画面：调虚拟时间流速/跳变，展示人格值回归。

**边界**

- 这是产品机制，技术门槛不高，容易被复刻。
- 衰减率/流速需要角色作者调参；调不好会“人设漂移”。
- 不是情感模型，不能替代真实语义理解。

## C. 宿主与生态

### 8. 能力画像的附着/替换/派生

**一句话**：桌面、VS Code 等多个宿主共享同一个“该怎么安置内核”的纯决策函数，各自在本地执行，保证一台机器只有一个内核写者。

**问题**

同一台机器上，桌面端和编辑器扩展都可能要拉起内核：

- 各拉一个 → 两个进程抢同一个数据库/端口；
- 直接附着 → 能力画像不匹配，功能缺失；
- 直接替换 → 可能打断正在用的宿主。

**做法**

1. 健康探测本机内核，拿二进制清单 + 发行版标识 + 能力画像摘要。
2. 组装统一输入：运行中内核、候选二进制、当前宿主画像、用户锁定、是否允许替换。
3. 纯决策函数输出：附着 / 替换并附着 / 派生最优 / 内置回退。
4. 宿主本地执行：附着走本机接口；替换先停旧再派生；派生注入端口/数据目录/角色目录/画像路径。
5. 单写者：只有内核进程写库，宿主不再内嵌写逻辑。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/host_profile.rs`
- `kernel/crates/oclive_kernel_host/src/infrastructure/capability_registry.rs`
- `kernel/crates/oclive_kernel_host/src/service/execution_plan.rs`
- `distros/*/distro.oclive.toml`

**和常见做法差在哪**

常见做法是“每个宿主自己判断要不要启动内核”；这里把判断抽成无副作用的共享决策，执行留给宿主。它解决的是“多宿主 + 单写者 + 画像兼容”三个约束同时成立的问题。

**视频钩子**

> “桌面和 VS Code 同时开着，为什么不会打架？”

可拍画面：两个宿主同时开，任务管理器只有一个内核进程；切换画像触发替换。

**边界**

- 单机范围；不是多机/多用户协调。
- 画像兼容判断是启发式，未知画像有升级路径但也有歧义。
- 替换会中断当前会话，产品要处理提示与恢复。

### 9. 插件能力双重校验 + 远程三级降级

**一句话**：高风险能力必须“清单声明 + 用户授权”同时成立；远程能力按未配置/未授权/不可用三级处理，不静默回退。

**问题**

插件系统常见两个漏洞：

- 清单声明了能力，但用户没授权，宿主却放行；
- 远程调用失败，直接回退本地，把“未授权出站”掩盖成“服务不可用”。

**做法**

1. 子进程派生：第一道校验清单是否声明 `process:spawn`，第二道校验用户是否授权；两道都过才派生。
2. 懒启动 + 按插件加锁 + 标准输出就绪握手，避免并发重复派生。
3. MCP 工具：按传输方式校验（stdio 对应子进程，http 对应出站网络）；未授权直接拒绝。
4. 组装工具描述时略去未授权工具，让模型“看不到”。
5. 远程能力三级：未配置 → 内置占位；未授权 → 硬失败不回退；已授权但不可用 → 按开关回退或报错。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/infrastructure/high_risk_grants.rs`
- `kernel/crates/oclive_kernel_host/src/service/high_risk.rs`
- `kernel/crates/oclive_kernel_host/src/infrastructure/directory_plugins/`
- `kernel/crates/oclive_kernel_host/src/infrastructure/remote_plugin/`

**和常见做法差在哪**

能力授权本身不新；“声明 + 授权双闸门”“未授权不回退”“三处能力键名一致”这套组合，把安全失败和可用性失败分开，避免“失败就用本地”掩盖越权。

**视频钩子**

> “插件说它要开子进程。它说了算，还是我说了算？”

可拍画面：未授权时拒绝；授权后派生；远程未授权硬失败，不偷偷回退。

**边界**

- 授权 UX 仍是产品问题；用户可能无脑点允许。
- 能力键名一致性靠测试锁，新增能力要同步三处。
- 不是进程级沙箱；恶意原生代码仍有宿主权限。

### 10. 插件 UI 沙箱

**一句话**：插件界面放进 opaque iframe，通过 parent broker 拿能力；能力令牌绑定插件，导航时撤销。

**问题**

插件 UI 如果和宿主同源/同 webview：

- 能读宿主 DOM、聊天内容；
- 能直接调宿主 IPC；
- 一个插件被导航到外部页面，令牌可能被带走。

**做法**

1. 发行构建禁止 inline Vue，插件 UI 走 opaque iframe sandbox。
2. 宿主与插件之间只通过 parent broker 通信；插件不直接拿宿主 IPC。
3. 能力令牌绑定插件身份；导航/卸载时撤销。
4. 保留 HTML fallback，并保证功能对等，避免“安全了但用不了”。
5. 原生 E2E 验证：宿主/另一个插件不可读、直接 IPC 被拒、broker 正向可用。

**代码锚点**

- `handoff/debt-marathon/long-plans/K-PLUGIN-SEC-01.md`
- `kernel/crates/oclive_kernel_host/src/service/plugin_bridge.rs`
- `distros/desktop-tauri/src/api/plugin_bridge.rs`
- `distros/shared/src/components/ChatPluginToolbarSlots.vue` 等插槽组件

**和常见做法差在哪**

Web 沙箱/iframe 隔离是成熟技术；这里的关键是“插件 UI 的默认运行形态 + 令牌生命周期 + HTML fallback 对等”。它不是进程沙箱，而是把“插件 UI 不可信”变成默认假设。

**视频钩子**

> “插件界面能不能偷看你的聊天记录？”

可拍画面：恶意示例尝试读宿主 DOM/直接 IPC，被拒绝；正常插件通过 broker 工作。

**边界**

- Stage 4 可信签名/身份绑定未完成；Windows CDP 证明仍是部分。
- 不是对抗恶意原生代码的沙箱；插件进程仍有 OS 权限。
- iframe 兼容性/性能有代价，需要 fallback。

### 11. 蓝图双视图编辑

**一句话**：磁盘只有一份 `pipeline.ocblueprint` 真源；编辑器拆成 manifest/settings 两个视图；保存时只保留高级扩展字段，不整体覆盖。

**问题**

角色包配置有三类读者：普通创作者、管理员/高级工具、运行时。常见做法是多份配置文件（manifest.json + settings.json），结果：

- 多真源漂移；
- 编辑器一保存，高级扩展字段被冲掉；
- 提示词正文和配置混在一起。

**做法**

1. 磁盘单一真源：`pipeline.ocblueprint`。
2. 加载时拆成 manifest（角色内容）与 settings（运行/后端）两个视图。
3. 保存时先用临时遗留文件形状重建蓝图，复用运行时同源构建逻辑。
4. 从旧蓝图中选择性保留 `includes` / `groups` / `expert_overlay` / `runtime_config`，不整体覆盖。
5. 写回蓝图、删除临时文件；提示词正文放独立资源，蓝图只留引用。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/infrastructure/role_pack.rs`
- `distros/chat-pro/roles/mumu/pipeline.ocblueprint`（示例角色包）
- 姊妹仓 `oclive-pack-editor` 的 `blueprintV2.ts`（位于该仓 `lib/` 目录）

**和常见做法差在哪**

双视图编辑器不新；“单真源 + 临时遗留形状复用 + 白名单扩展字段保留”这个组合，解决的是“普通创作者不丢高级配置、运行时不为编辑器改格式”的两难。

**视频钩子**

> “我在编辑器里改了一个角色，为什么管理员写的高级配置没丢？”

可拍画面：改 manifest → 保存 → 检查 `includes/expert_overlay` 仍在。

**边界**

- 保存过程中会短暂产生临时遗留文件；异常退出要清理。
- 保留字段是白名单，新增扩展字段要同步维护。
- 不是通用 schema 合并器；只处理预设字段。

## D. 交互与内容

### 12. 共在/异地与场景位移

**一句话**：每轮先判断“角色在不在用户身边”，再决定走完整处理还是简化处理；位移意图规则优先、模型兜底，同行优先于目的地选择。

**问题**

角色“在身边”和“在异地”是两种存在状态。如果都按共在处理：

- 异地时也更新好感/记忆，状态被污染；
- 用户说“我去河边”，系统分不清是“告诉你”还是“邀请你一起去”；
- 位移后场景不切换，下一轮还判错。

**做法**

1. 校验用户在场场景；与角色当前场景比较：无场景/相同 → 共在，不同 → 异地。
2. 异地：简化处理（只做情绪/固定回复，或生成内心独白；不更新好感/记忆）。
3. 共在：完整处理；对位移意图先规则（位移动词 + 地点/同行关键词），不命中再模型兜底。
4. 命中位移：若“邀请一起去”→ 同行确认（优先）；否则 → 目的地选择。
5. 用户确认后切换场景；一起走 → 下一轮仍共在；单独走 → 下一轮可能异地。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/chat_engine/presence.rs`
- `.../chat_engine/scene.rs`
- `.../turn_pipeline/remote_life.rs`
- `.../process_message.rs` 的共在/异地分支

**和常见做法差在哪**

“角色有场景”不新；把“存在状态”做成每轮第一判定，并让两条路径的状态更新粒度不同，是产品语义 + 运行时分支的结合。它避免“异地聊天也涨好感”的常见 bug。

**视频钩子**

> “她是在你身边，还是在异地？这句话决定了这轮要不要涨好感。”

可拍画面：同一句话在共在/异地两种状态下的不同处理与状态变化。

**边界**

- 位移意图识别靠规则 + 模型，仍会误判。
- 异地简化处理是产品选择，不是唯一正确答案。
- 场景切换涉及前端交互，端到端体验仍需打磨。

### 13. 预生成骨架 + 本地局部补丁

**一句话**：强模型离线写高质量骨架，运行时只让本地小模型改“被用户动过的那几个节拍”。

**问题**

剧情对话要同时满足：高质量、低时延、低成本、可微改。全场用强模型在线生成，贵且慢；全场用本地小模型，质量不够；用户改一个变量就全场重生成，浪费。

**做法**

1. 强模型离线生成骨架：按节拍组织的固定文本 + 变量占位 + 变量到节拍的影响映射。
2. 运行时按骨架逐节拍播放，零模型调用。
3. 只暴露少数“高含金量变量”给用户微改（性格、处境、称呼等）。
4. 用户改变量 → 按影响映射定位受影响节拍 → 只对这些节拍调本地小模型改写。
5. 改写期间显示“加载中”遮时延；完成后接回固定骨架；本地模型不可用则回退默认文本。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/infrastructure/db/adult_stage.rs`
- `distros/shared/src/lib/adultBeatQueue.ts`
- 迁移 `038`

**和常见做法差在哪**

分层生成/粗到细不新；“预生成骨架 + 变量影响映射 + 局部有界补丁 + 加载遮时延”把成本和质量解耦：强模型成本一次性，本地模型只做短文本改写。

**视频钩子**

> “大模型写骨架，小模型打补丁——用户改一句话，只重写一小段。”

可拍画面：改一个变量，只有局部节拍变化，其余保持高质量固定文本。

**边界**

- 目前主要服务特定剧情内容（成人节拍）；不是通用对话。
- 局部补丁质量取决于本地小模型；约束太松会跑偏。
- 变量/影响映射需要内容作者维护。

### 14. 规则门控二次改写

**一句话**：主回复生成后，先用规则判断“值不值得改”；命中才调本地模型改写，失败就直通原回复。

**问题**

对所有回复都做二次改写，浪费推理；改写失败如果中断对话，体验更差；不同角色需要不同的改写风格。

**做法**

1. 读角色配置：是否启用后处理、用哪个后端。
2. 规则门：复述用户、出现不期望的标记/代码块、长度超限等，命中才改写；不命中直通并记录跳过原因。
3. 按角色取/建改写预设（优先角色包显式指引，否则核心人设 + 质量锚点），按角色缓存。
4. 本地模型改写；未配置模型则直通。
5. 改写失败/超时/空结果 → 返回主回复，对话继续。

**代码锚点**

- `kernel/crates/oclive_kernel_host/src/domain/chat_engine/turn_pipeline/post/post_llm.rs`
- `kernel/crates/oclive_kernel_contracts/src/reply_post_processor.rs`
- 角色包 `config.json` 的回复后处理配置

**和常见做法差在哪**

“回复后处理”不新；“规则门控 + 按角色预设缓存 + 失败直通 + 正交于六槽”这套组合，把改写从“每次都做”变成“值得才做”，并且不让它成为对话单点故障。

**视频钩子**

> “不是每句话都值得再算一遍。”

可拍画面：合格回复直通；触发规则才改写；关掉本地模型，对话照常。

**边界**

- 规则是启发式，会漏/误判。
- 改写质量取决于本地模型和人设预设。
- 不是安全过滤，不能替代内容审核。

## E. 事件

### 15. Event Ring 权威事件环

**一句话**：给事件签发可信的身份、来源、权重和因果链；模块只能按声明订阅/提案，不能冒充别人，也不能绕过编排。

**问题**

多模块系统里，“谁知道发生了什么”很容易失控：

- 模块直接改状态、伪造来源；
- 事件总线变成第二套回复引擎；
- 事件没有因果链，出问题无法追踪。

**做法**

1. 事件信封带身份、来源、基础影响权重、顺序、因果链；权重是定点比例（10000 = 1.0）。
2. 源绑定 emitter：模块只能以自己的身份发事件，不能冒充别的来源。
3. 模块声明订阅/优先级；注册策略决定失败是快速失败还是隔离。
4. 模块只能返回 payload 替换/元数据/子事件，不能直接改信封身份字段。
5. 进程内、有界、不写数据库；默认关闭的 trace-only 只记脱敏事实头，不影响结果。

**代码锚点**

- `kernel/crates/oclive_kernel_contracts/src/event_ring.rs`
- `kernel/crates/oclive_kernel_host/src/infrastructure/directory_plugins/event_ring.rs`
- `creator-docs/plugin-and-architecture/EVENT_RING.md`

**和常见做法差在哪**

发布/订阅不新；这里把“权威”限制在信封身份与注册策略，明确它不拥有状态提交权、不是第二套 pipeline、不是数据库事件总线。对多模块 AI 运行时，这是一条重要的边界。

**视频钩子**

> “角色怎么知道‘刚才发生了什么’？谁有资格说这件事发生了？”

可拍画面：模块发事件 → Ring 路由 → 订阅模块处理；伪造来源被拒。

**边界**

- 不是持久化事件流；Runtime Event Stream 仍未生产化。
- 不判断外部事实真伪，只保证来源/身份/因果。
- trace-only 默认关闭，不等于可观测性完整。
