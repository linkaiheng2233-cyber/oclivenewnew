# RFC: oclive high-coupling compile mode (Monolith / weld mode)

| Metadata | Value |
|----------|--------|
| Status | **Shipped**: `oclive-cli` provides **`init` / `build` / `bench`**, weld-plan validation, dual entrypoints **`main.rs` + `main_monolith.rs`**; **seven weld-key** static entrypoints in **`vendor/oclive_monolith_builtin`** (template under `kernel/crates/oclive-cli/monolith_vendor/`) are canonical and may be replaced with real `oclive_*_builtin`. |
| Entry | **`oclive init`** creates scaffolds; **`cargo run -p oclive-cli -- --experimental build|bench`** maintains and compares Monolith artifacts |
| Compile config | **`monolith.toml`**: generated by `init`, read by **`oclive build`** to regenerate `process_message_monolith.rs`; **not runtime**, unrelated to role pack / host load paths |
| vs blueprint boundary | **`pipeline.ocblueprint`** (or `*.ocblueprint`) describes **runtime** orchestration; **weld scope is not carried in blueprint fields** (avoid conflating with `PIPELINE_SCHEMA` runtime semantics). Monolith applies only via **`monolith.toml` + Cargo feature**. |
| Audience | **Developers only**; end users only run developer-built releases and do not touch the terminal |
| Essence | **Compile-time** optimization path: trade module swappability for peak performance (optional, off by default), to break the **hot-path ceiling** of the **modules 1–6** abstraction |

**Related**: [`OCLIVE_ARCHITECTURE_OVERVIEW.md`](../getting-started/OCLIVE_ARCHITECTURE_OVERVIEW.md) (numbering), [`PLUGIN_V1.md`](../plugin-and-architecture/PLUGIN_V1.md) (modules 1–6 + `PluginHost`), [`PIPELINE_SCHEMA.md`](../../creator-docs/kernel/PIPELINE_SCHEMA.md) (blueprint runtime schema), [`OCLIVE_CLI_GUIDE.md`](../cli/OCLIVE_CLI_GUIDE.md) (scaffold usage).

**Matches `main`**: `cargo run -p oclive-cli -- --experimental init … --monolith` (non-interactive, **kernel_server** project type) or interactive “high coupling” generates **`monolith.toml`**, `vendor/oclive_monolith_builtin/`, `src/process_message_monolith.rs`, and declares **`[features] monolith`** plus second **`[[bin]]`**. After editing `monolith.toml`, **`cargo run -p oclive-cli -- --experimental build -o <project root>`** regenerates weld sources and by default runs `cargo build` twice (second with **`monolith`** feature when `enabled = true`). **`cargo run -p oclive-cli -- --experimental bench`** emits JSON latency reports (schema: `kernel/crates/oclive-cli/schemas/oclive_bench_report.schema.json`). **library** projects ignore `--monolith` and do not emit `monolith.toml`.

## 1. Problem statement

The **six host backend modules (modules 1–6)** plugin architecture (`plugin_backends` + `PluginHost` + trait facades) delivers **ecosystem flexibility** (builtin / remote / directory, sidecars, directory plugins) but adds **architectural overhead**:

- **Trait virtual calls**: multiple dynamic dispatches on the `process_message` orchestration chain;
- **Inter-module DTOs**: generality often implies heap allocation and copy paths at boundaries (“serialization” here means any packing cost across abstraction boundaries, not only JSON);
- **Locks and runtime structures**: independent locks per subsystem can show contention and sync cost on hot paths.

For **high-frequency** scenarios that **do not need swappable modules** (game NPCs, real-time voice, embedded characters), the ceiling is **architectural**: not just one algorithm, but **accumulated boundary cost**.

This RFC proposes **high-coupling compile mode (Monolith)**: developers declare weld scope via scaffold + **`monolith.toml`**, and at **compile time** selected modules become **static calls into concrete implementations**, breaking the hot-path ceiling of the low-coupling plugin stack alone; unwelded modules still use **`PluginHost` + traits**.

## 2. Design goals

| Goal | Notes |
|------|--------|
| **Entry in scaffold only** | Expose “developer compile options” only in **`oclive init`**; **not** in desktop settings or any GUI. |
| **Paired with `monolith.toml`** | Scaffold **generates** `monolith.toml`; **`oclive build`** (or project `build.rs`/xtask) **reads** it at compile time to choose weld set and generate code. **This file is not loaded at runtime.** |
| **Compile-time optimization artifact** | With **`Cargo` feature `monolith`**, compile or generate a **second** orchestration implementation removing **welded** trait virtual calls, producing a comparable second binary (see section 3 naming). |
| **End users unaware** | Users only install/run **pre-built** binaries; welding decisions are **developer build-time** only. |
| **Break architectural perf limits** | Optional path for **latency-sensitive** cases that explicitly give up some swappability, **long-term coexisting** with standard low-coupling mode. |

## 3. Scaffold interaction design

Target **`oclive init`** interaction after this RFC (copy can change, behavior must not). The repo entry remains **`cargo run -p oclive-cli -- init`**.

```text
$ oclive init my-fast-npc
  Welcome to the oclive scaffold!
  ? Project name: my-fast-npc
  … (existing steps: role pack, modules 1–6 backends, etc.)
  ? Enable developer compile options? [y/N]: y
```

Inside developer compile options:

```text
  ? Compile mode:
    ● Standard (low coupling, keeps swappable modules, recommended)
    ○ High coupling — weld all seven keys statically (modules 1–6 + `complex_emotion`)
    ○ High coupling — custom weld scope (edit monolith.toml then run oclive build)
```

Target **artifact naming** when generation completes (both builds can coexist for comparison):

```text
  Project created!
    Standard binary:     target/release/my-fast-npc
    Monolith binary:     target/release/my-fast-npc-monolith
```

### 3.1 Key constraints

1. **Default is always “standard”**: “Enable developer compile options” defaults **`N`**; inside, **standard** is pre-selected.
2. **`-monolith` suffix**: high-coupling Release binary name must differ from default; **must not overwrite** `target/release/<name>`.
3. **Both builds coexist**: same `Cargo.toml` via **`feature = "monolith"`** and/or second **`[[bin]]`** / different output names; CI and local can `cargo build` / `cargo build --features monolith` separately.

## 4. Pairing with `monolith.toml`

### 4.1 File responsibilities

| File | Lifecycle | Notes |
|------|-----------|--------|
| **`monolith.toml`** | **Compile-time only** | Generated/updated by **`oclive init`**; read by **`oclive build`**; **not** shipped with role packs, **not** parsed by host `load_role`. |
| **`pipeline.ocblueprint` etc.** | **Runtime** (if blueprints used) | **Decoupled** from Monolith; weld scope **must not** live inside blueprint JSON to avoid locking to `PIPELINE_SCHEMA` evolution. |

### 4.2 Suggested TOML format (pick one)

**Explicit weld list** (`exclude` must be empty array):

```toml
[monolith]
enabled = true
weld_modules = ["emotion", "memory", "prompt", "llm"]
exclude = []
```

**Weld all then exclude** (`weld_modules` must be empty array):

```toml
[monolith]
enabled = true
weld_modules = []
exclude = ["event", "agent", "complex_emotion"]
```

### 4.3 Field semantics

| Field | Semantics |
|-------|-----------|
| **`enabled`** | Whether Monolith compile path is enabled for this project (generates `process_message_monolith.rs` or equivalent, and enables `monolith` feature-related cfg). |
| **`weld_modules`** | Keys to weld (**seven weld keys**: modules 1–6 + `complex_emotion` facility weld key). **Empty array** means **weld all weldable keys** (then apply `exclude`). |
| **`exclude`** | Valid **only when `weld_modules` is empty**: subtract from the “weld all” set; excluded slots remain **`PluginHost` + trait** placeholders in generated code. |

**Validation (current impl)**: **`weld_modules` and `exclude` must not both be non-empty**; slot names must be one of the seven keys. When `enabled == false`, **`oclive build`** still regenerates `process_message_monolith.rs` but **skips** the second `cargo build --features monolith`.

### 4.4 Scaffold and build behavior

- **`oclive init`**: writes `monolith.toml` and vendor template snippets when developer chooses high coupling.
- **`oclive-cli --experimental build`** (`cargo run -p oclive-cli -- --experimental build`): reads `monolith.toml`, validates, generates `process_message_monolith.rs` and `vendor/oclive_monolith_builtin`; by default runs **`cargo build`** twice (second with **`monolith`** feature when `enabled = true`). `--no-cargo` generates only; `--release` and `--features` pass through to `cargo build`.
- **`oclive bench`**: after regen + dual builds, runs each binary `--runs` subprocess times (hot loop `OCLIVE_KERNEL_BENCH_ITERS` inside), outputs JSON (see schema).

## 5. Technical approach summary

### 5.1 Cargo feature: `monolith`

- Add **`monolith`** feature (name may be finalized; this doc uses `monolith`).
- **Disabled**: `process_message` keeps **`pl.<module>…`** trait virtual calls.
- **Enabled**: for welded modules, **direct calls** into concrete implementations (illustrative):

```rust
// Low coupling (today)
pl.emotion.analyze(&input);
pl.memory.rank_memories(&input);

// High coupling (target shape; symbols follow stable weld API)
oclive_emotion_builtin::analyze(&input);
oclive_memory_builtin::rank_memories(&input);
```

Unwelded modules **still** use **`PluginHost` + traits**.

### 5.2 Code generation driven by `monolith.toml`

- **`oclive init`** / **`oclive build`** generate or refresh **`src/process_message_monolith.rs`** (or equivalent) from **`weld_modules`** / **`exclude`**:
  - Welded subsystems: static calls;
  - Others: keep `pl.*`;
  - Main entry switches via **`cfg(feature = "monolith")`**, `include!`, or thin wrappers to avoid full-file duplication (implementation detail TBD).

### 5.3 Relationship to the main repo

The main repo must eventually expose a **stable weld symbol boundary** (public `fn` or small facade crates); otherwise generated projects depend on `pub(crate)` internals with high upgrade cost (see section 8).

## 7. Expected benefits

- Remove **trait virtual calls** for **welded modules** on the hot path (fewer dynamic dispatches per `process_message` depending on depth).
- **Stack-pass DTOs** inside weld boundaries, fewer heap allocs and copies across boundaries.
- **Lock merging / smaller critical sections** may be feasible for some module combos, **not automatic**, needs audit.
- **Smaller binaries**: unused backend implementations may benefit from trimming + LTO (depends on link units).

Concrete numbers come from **`oclive bench`** (section 9); this RFC **makes no promises**.

---

## 8. Risks and limitations

- **Welded modules cannot hot-swap**: cannot switch to remote/directory via marketplace or `settings.json`; changes require **recompile**.
- **Dual-path maintenance**: `monolith` and default paths must evolve together; test matrix grows.
- **Perf gains need benchmarks**: when network I/O or LLM dominates, welding may not help.
- **API and symbol stability**: binding directly to implementations increases upgrade coupling; needs a separate “weld API layer” design.

## 9. Roadmap status (aligned with `main`)

| Phase | Status |
|-------|--------|
| **Phase 1 (scaffold)** | **Done**: `oclive-cli init` supports **`--monolith`** (non-interactive) and interactive “developer compile options”; generates **`monolith.toml`**, **`vendor/oclive_monolith_builtin/`** (**canonical** for seven weld-key static entry), **`process_message_monolith.rs`**; **dual `[[bin]]`** with **`src/main.rs`** / **`src/main_monolith.rs`**; `cargo test -p oclive-cli` includes release dual-build E2E. |
| **Phase 2 (custom weld)** | **Done**: **`weld_modules` / `exclude`** mutual exclusion validation, partial weld codegen; **`oclive build`** reads `monolith.toml`, regenerates weld sources, optional dual build. |
| **Phase 3 (`oclive bench`)** | **Done**: **`oclive bench`** compares standard vs **`-monolith`** binaries, JSON output (schema: `kernel/crates/oclive-cli/schemas/oclive_bench_report.schema.json`). |
| **Phase 4 (real symbols)** | **Done (vendor path)**: welded keys statically link **`oclive_monolith_builtin`**; the main repo does **not** duplicate weld stubs inside `src-tauri`. If **`oclive_*_builtin`** crates are split later, only generated project deps and call sites change; scaffold **still** treats `kernel/crates/oclive-cli/monolith_vendor/oclive_monolith_builtin/` as template canonical source. |
